# [백엔드 → 프론트] 세션 ID 발급/전달 방식 확인 요청

- 작성: 백엔드
- 버전: v0.1 (draft) → **결정: A. 커스텀 헤더 (`X-Session-Id`) 방식으로 확정**
- 목적: Spring Security 도입을 앞두고, `session_id` 발급/전달 방식을 프론트와 맞추기 위한 확인 요청

> **[결정사항]** 프론트-백엔드 협의 결과 아래 "확인 요청 사항 1"은 **A안(커스텀 헤더, `X-Session-Id`)** 로 확정되었습니다. 나머지 확인 요청 사항(2, 3)은 아직 미정입니다.

## 배경

- MALLO는 회원가입/로그인이 없는 MVP입니다. 유저를 구분하는 개념 자체가 없고, **`session_id`(= Recovery Journey 식별자) 하나로 모든 데이터를 구분**합니다.
- `session_id`는 **백엔드가 발급**합니다 (`POST /v1/sessions` 응답으로 내려줌).
- 최근 백엔드에서 **Spring Security 도입 결정**이 나왔습니다. 단, 로그인이 없으므로 "인증(누가 로그인했는지)"이 아니라 **"인가(이 요청이 해당 session_id의 데이터에 접근할 자격이 있는지)"** 용도로 씁니다. 사실상 `session_id` 자체가 발급된 토큰처럼 쓰이는 구조입니다.

## 확인이 필요한 이유

저희 쪽에 있던 초안 문서(`MALLO_Backend_Routing_Logic_Draft_MVP.json`)를 보면 엔드포인트가 아래처럼 경로변수 없이 플랫하게 정의돼 있고,

```
POST /v1/checks
POST /v1/ask
POST /v1/photos/analyze
```

각 흐름의 첫 단계가 "session_id 검증"으로 되어 있어서, **`session_id`를 요청 바디(JSON)에 필드로 담아 보내는 것**을 전제로 한 문서로 보입니다. 그런데 이 초안이 실제 프론트 구현과 다를 수 있다고 하셔서, 확정된 방식을 다시 확인하려고 합니다.

전달 방식에 따라 백엔드에서 Security를 붙이는 구현이 달라집니다:

| 방식 | 설명 | 비고 |
| --- | --- | --- |
| **A. 커스텀 헤더** (예: `X-Session-Id`) | 모든 요청에 헤더로 실어서 보냄 | Security Filter에서 일괄 검증 가능, URL/바디에 ID 노출 안 됨, 구현 깔끔 (백엔드 추천) |
| **B. URL 경로변수** (예: `/v1/journeys/{sessionId}/...`) | 리소스 경로에 세션 ID 포함 | REST스럽지만 리소스마다 경로 패턴을 개별 매칭해야 해서 구현이 번거로움 |
| **C. 요청 바디 필드** (기존 초안 방식) | JSON body에 `session_id` 필드로 포함 | Security 표준 Filter 체인(바디 읽기 전 동작)으로는 처리 안 되고, 서비스/컨트롤러 레벨에서 별도 검증 필요 |

## 확인 요청 사항 (1차 — 완료)

1. ~~**`session_id` 전달 방식**: 위 A/B/C 중 어떤 방식으로 프론트가 요청을 보낼 계획인가요?~~ → **결정 완료: A. 커스텀 헤더(`X-Session-Id`)**
2. ~~**세션 생성 이후 저장 방식**~~ → **답변 완료: `SecureStore`에 저장**
3. ~~**세션 만료/재발급**~~ → **답변 완료: 새로운 Recovery Journey 시작 시마다 새 세션 발급** (아래 2차 확인에서 세부 트리거 조정 중)

## 참고: 백엔드 쪽 결정 사항 (변경 가능, 공유 차원)

- `session_id`는 **UUID**로 발급 예정 (순차 증가값 대신, 추측/열거 공격 방지 목적)
- 도메인 구조: `journey`(Protocol 포함), `image`(파일은 로컬 저장, 경로만 DB 저장), `sessionInfo`(발급된 세션 목록/상태 관리)로 구성 예정
- `MALLO_최종_기획.docx`(PRD)의 ERD에 있는 `LOCAL_PROFILE` 엔티티는 **테이블로 만들지 않기로 결정**. 회원 개념이 없어서 실질적으로 `session_id` 자체가 최상위 식별자 역할을 하고, PRD의 ERD는 백엔드가 자체적으로 재해석한 설계 기준으로 대체함 (ERD 원본은 참고만 하고 그대로 따르지 않음)

## 2차 확인 요청 — 세션 상태/재진입 흐름

프론트에서 제안한 흐름(아래) 확인했고, 백엔드 입장에서 검토한 답변입니다.

> - `POST /v1/sessions`에서 발급받은 `session_id`를 SecureStore에 저장
> - 이후 API 요청 시 `X-Session-Id` 헤더로 전달
> - 새로운 Recovery Journey 시작 시 새 세션 발급
> - 기존 Journey가 있으면 저장된 세션 재사용
> - 앱 재실행 시에는 저장된 세션의 활성 여부를 확인한 후 기존 Journey로 진입

### 🖐 질문 1. 앱 재실행 시 활성 세션 확인 방식 — **문제없음, 방식 제안**

별도의 "세션 상태 체크" 전용 엔드포인트를 새로 만들지 않고, 기존 계약에 있는 **`GET /v1/sessions/today`를 그대로 재사용**하는 방식을 제안합니다.

- 앱 실행 시 SecureStore의 `session_id`를 `X-Session-Id` 헤더에 실어서 `GET /v1/sessions/today` 호출
- **200 + `status: ACTIVE`** → 기존 Journey로 진입 (S04)
- **404 (세션 없음) 또는 `status: COMPLETED`** → "활성 세션 없음"으로 간주 → 새 Journey 시작 플로우로 유도 (S02 → S03)

→ 프론트가 이 방식으로 진행해도 괜찮을지, 아니면 별도 엔드포인트(예: `GET /v1/sessions/status`)가 더 편한지 의견 부탁드립니다.

### 🖐 질문 2. 새 Journey 시작 = 새 session_id 발급 — **확인, 맞습니다**

`POST /v1/sessions`는 호출될 때마다 새 UUID로 새 row를 생성합니다. 프론트는 SecureStore 값을 새 `session_id`로 덮어쓰면 됩니다. (이전 세션 데이터는 DB에 남지만 더는 참조되지 않는 상태가 됩니다.)

### 🙋 백엔드 → 프론트 역질문. 세션 종료(`ACTIVE → COMPLETED`) 트리거는 언제인가요?

`session_status` enum은 기존 계약대로 `ACTIVE` / `COMPLETED` 2가지를 유지할 계획인데, **`COMPLETED`로 바뀌는 시점을 프론트 UX와 맞춰야 해서** 여쭤봅니다. PRD 990줄에는 "DAY 7 이후에도 Recovery Session은 유지한다"고 되어 있어서, 자동 만료는 아닌 것 같은데:

| 옵션 | 내용 |
| --- | --- |
| **A. 수동 종료** | 사용자가 화면에서 "회복 여정 종료" 같은 버튼을 직접 눌러야 `COMPLETED`로 전환 |
| **B. 자동 종료** | 특정 DAY(예: DAY 7, DAY 30 등)가 지나면 백엔드가 자동으로 `COMPLETED` 처리 |
| **C. MVP 범위 제외** | 해커톤 데모 시간 안엔 종료 시나리오 자체가 안 나오므로, `COMPLETED` 전환 로직 자체를 안 만들고 사실상 계속 `ACTIVE` 유지 |

- 화면 설계(IA/와이어프레임) 상에 "여정 종료" 관련 화면/버튼이 있는지, 있다면 A로 가는 게 맞고
- 없다면 C(미구현)로 가고 나중에 필요해지면 추가하는 방향이 무난해 보입니다.

→ 프론트/디자인 쪽에 해당 화면이 있는지 확인 부탁드립니다.
