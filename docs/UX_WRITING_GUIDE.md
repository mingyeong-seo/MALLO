# 1. 목적

MALLO의 모든 화면에서 사용자가 문구와 화면을 빠르게 이해하고, **지금 무엇을 해야 하는지 쉽게 판단할 수 있도록** 공통 UX 기준을 정의합니다.

토스 UX Writing / Consumer UX Guide의 원칙을 참고하되, 그대로 복제하지 않고 MALLO의 서비스 성격에 맞게 적용합니다.

MALLO는 **시술 후 회복 행동을 안내하는 서비스**이므로 일반적인 UX Writing 원칙과 함께 다음 기준을 중요하게 봅니다.

```
쉽게 이해할 수 있는가?
↓
지금 필요한 정보만 보여주는가?
↓
다음 행동을 예상할 수 있는가?
↓
사용자의 선택을 존중하는가?
↓
의료적 판단과 행동 안내의 경계가 명확한가?
```

---

# 2. MALLO Writing 원칙

MALLO의 문구는 아래 6가지 원칙을 기준으로 작성합니다.

```
Clear
명확하게

Concise
간결하게

Predictable
다음 행동을 예상할 수 있게

Casual
쉽고 자연스럽게

Respectful
사용자의 선택을 존중하게

Safe
의료·회복 정보는 안전하고 명확하게
```

## Clear — 한 번에 이해할 수 있게 씁니다

- 어려운 단어보다 일상적인 표현을 사용합니다.
- 한 문장에는 가능한 한 하나의 메시지만 담습니다.
- 개발자나 기획자가 아니라 **사용자가 이해할 수 있는 표현**을 사용합니다.

## Concise — 중요한 정보만 남깁니다

- 없어도 의미가 달라지지 않는 단어는 제거합니다.
- 화면이 비어 보인다는 이유로 설명을 추가하지 않습니다.
- 제목과 본문에서 같은 내용을 반복하지 않습니다.
- 사용자가 이미 화면에서 확인할 수 있는 정보를 다시 설명하지 않습니다.

## Predictable — 다음 행동을 예상할 수 있게 씁니다

- 버튼만 읽어도 다음 화면이나 행동을 예상할 수 있어야 합니다.
- `다음`, `확인`, `완료`처럼 결과를 알기 어려운 CTA는 최소화합니다.

## Casual — 말하듯 자연스럽게 씁니다

- 기본적으로 해요체를 사용합니다.
- 지나치게 공식적이거나 딱딱한 경어를 피합니다.
- 실제로 소리 내어 읽었을 때 어색하지 않은 표현을 사용합니다.

## Respectful — 선택을 강요하지 않습니다

- 불필요한 공포감이나 긴급함을 만들지 않습니다.
- 사용자가 스스로 다음 행동을 결정할 수 있게 안내합니다.
- 뒤로 가기, 닫기, 선택하지 않기 등의 선택권을 불필요하게 막지 않습니다.

## Safe — 의료적 판단보다 안전한 행동 안내를 우선합니다

- MALLO가 사용자의 피부 상태를 진단한 것처럼 표현하지 않습니다.
- 검수된 Recovery Protocol 범위에서 행동 기준을 안내합니다.
- 의료진 확인이 필요한 상황은 완곡하게 숨기지 않고 명확하게 안내합니다.

# 3. 개발 용어와 사용자 언어를 분리합니다

MALLO의 **기획/코드/API에서 사용하는 이름과 사용자에게 보여주는 이름은 같을 필요가 없습니다.**

개발 과정에서 명확한 영문 명칭은 그대로 유지하되, 사용자 화면에서는 이해하기 쉬운 표현으로 변환합니다.

## 기능명

| 내부 기획/개발명    | 사용자 노출명          |
| ------------------- | ---------------------- |
| `Today Action Plan` | **오늘의 회복 가이드** |
| `Recovery Record`   | **오늘 기록하기**      |
| `Recovery Journal`  | **회복 기록**          |

따라서 코드, 파일명, Route, API 등의 내부 이름은 기존 구조를 유지할 수 있습니다.

예:

```
TodayActionPlan
RecoveryRecord
RecoveryJournal

today-plan.tsx
record.tsx
journal.tsx
```

사용자 화면에서는:

```
오늘의 회복 가이드
오늘 기록하기
회복 기록
```

으로 표시합니다.

**내부 구조를 한국어로 변경하는 것이 아니라 사용자에게 노출되는 Label / Title / CTA를 변경합니다.**

---

# 4. Decision도 개발 상태값과 사용자 문구를 분리합니다

다음 값은 프론트엔드와 백엔드가 결과를 구분하기 위한 **내부 Decision 값**입니다.

```
POSSIBLE
ADJUST
POSTPONE
CONNECT
```

API와 TypeScript에서는 그대로 유지합니다.

예:

```
decision: "POSTPONE"
```

하지만 사용자에게 `POSTPONE` 등의 영문 상태값을 직접 보여주지 않습니다.

## Decision Mapping

| 내부 Decision | 사용자 노출 문구             | 의미                        |
| ------------- | ---------------------------- | --------------------------- |
| `POSSIBLE`    | **가볍게 진행할 수 있어요**  | 현재 조건에서 행동 가능     |
| `ADJUST`      | **조절해서 진행해요**        | 강도나 방법을 조절          |
| `POSTPONE`    | **오늘은 미루는 게 좋아요**  | 오늘은 행동을 미루도록 안내 |
| `CONNECT`     | **의료진의 확인이 필요해요** | MALLO의 판단 범위를 벗어남  |

구조:

```
Backend / Frontend 내부 상태

POSTPONE

        ↓

사용자 화면

오늘은 미루는 게 좋아요
```

**Decision은 시스템이 이해하기 위한 값이고, 사용자에게는 행동의 의미를 보여줍니다.**

---

# 5. 기본 말투는 해요체를 사용합니다

사용자에게 노출되는 설명과 안내 문구는 기본적으로 `~해요` 형태로 통일합니다.

### 지양

```
오늘은 강도 높은 운동을 미루는 편이 좋습니다.
```

### 권장

```
오늘은 강도 높은 운동을
미루는 편이 좋아요.
```

### 지양

```
사진 없이도 기록할 수 있습니다.
```

### 권장

```
사진 없이도 기록할 수 있어요.
```

단, 화면 제목이나 기능명 등 **UI Label을 억지로 해요체로 변경하지 않습니다.**

예:

```
Recovery Journey
Quick Check
Recovery Protocol
ASK MALLO
DAY 3
```

# 6. 능동적으로 말합니다

가능한 경우 수동형보다 사용자의 행동 또는 서비스의 행동이 보이는 문장을 사용합니다.

### 지양

```
Recovery Protocol 기준으로 확인됩니다.
```

### 권장

```
Recovery Protocol을 기준으로 확인해요.
```

### 지양

```
오늘의 회복 가이드에 반영됩니다.
```

### 권장

```
오늘의 회복 가이드에 반영할게요.
```

단, 수동형이 더 명확한 상황에서는 억지로 능동형으로 변경하지 않습니다.

---

# 7. 지나치게 딱딱한 경어를 사용하지 않습니다

### 지양

```
확인하시겠어요?
선택하시겠어요?
진행하시겠습니까?
문의하시겠습니까?
```

### 권장

```
확인할까요?
선택해 주세요
계속할까요?
의료진에게 문의할까요?
```

사용자의 상황을 추정하거나 정중한 확인이 필요한 경우에는 제한적으로 경어를 사용할 수 있습니다.

---

# 8. 어려운 명사형 표현을 줄입니다

화면 제목이나 메뉴가 아니라면 `{명사} + {명사}`를 반복하기보다 동사 형태로 풀어씁니다.

### 지양

```
조건 선택 완료
기록 저장 완료
상담 요청 완료
```

### 권장

```
조건을 선택했어요
기록을 저장했어요
상담을 요청했어요
```

화면 제목이나 기능명은 짧은 명사형을 사용할 수 있습니다.

```
Quick Check
회복 기록
오늘의 회복 가이드
설정
```

# 9. 한 화면에서 핵심 메시지는 하나만 전달합니다

사용자에게 지금 필요한 내용만 보여줍니다.

### 지양

```
오늘 운동을 할 예정인가요?
운동 시간과 운동 강도를 선택해 주세요.
회복 상태에 따라 운동 가능 여부가 달라질 수 있어요.
```

### 권장

S06:

```
어떤 행동을 확인할까요?
```

S07:

```
오늘 하려는 운동 강도는
어느 정도인가요?
```

선택:

```
가벼운 활동
중간 강도
고강도
```

# 10. 의미 없는 단어를 제거합니다

넣거나 빼도 의미가 달라지지 않는 표현을 줄입니다.

### 지양

```
현재 지금 확인할 수 있는 정보를 보여드릴게요.
```

### 권장

```
확인한 내용을 보여드릴게요.
```

단순히 글자 수를 줄이는 것이 아니라 **의미 없는 표현을 제거하는 것**을 우선합니다.

---

# 11. 같은 말을 반복하지 않습니다

화면이 비어 보인다는 이유로 의미 없는 문장을 추가하지 않습니다.

### 지양

```
DERNA의 시술 정보를 불러올까요?

최근 시술 정보를 불러와
시술 정보를 확인할 수 있어요.
```

### 권장

```
DERNA의 시술 정보를 불러올까요?

최근 시술 정보를 확인하고
맞춤 회복관리를 시작할 수 있어요.
```

**공간을 채우기 위한 문구보다 여백을 유지하는 것을 우선합니다.**

---

# 12. 버튼은 다음 행동을 알려줍니다

CTA는 버튼을 눌렀을 때 **다음에 무슨 일이 일어나는지 예상할 수 있도록** 작성합니다.

### 지양

```
다음
확인
완료
계속
자세히 보기
```

### 권장

```
시술 정보 불러오기
이 시술로 시작하기
결과 확인하기
오늘 계획에 반영하기
저강도 대안 보기
나중에 다시 확인하기
의료진에게 문의하기
사진 추가하기
기록 저장하기
```

기능명이 `오늘의 회복 가이드`라고 해서 CTA에서 반드시 전체 기능명을 반복할 필요는 없습니다.

예:

```
오늘의 회복 가이드에 반영하기
```

보다:

```
오늘 계획에 반영하기
```

처럼 **의미를 유지하면서 짧게 표현할 수 있습니다.**

# 13. 긍정형을 우선하되 명확성이 더 중요합니다

일반적인 안내에서는 사용자가 할 수 있는 행동을 중심으로 설명합니다.

### 지양

```
운동하면 안 돼요.
```

### 권장

```
오늘은 가벼운 활동으로
조절하는 게 좋아요.
```

### 지양

```
지금은 화장할 수 없어요.
```

### 권장

```
오늘은 화장을
미루는 게 좋아요.
```

단, 의료·안전 관련 내용처럼 사용자가 반드시 알아야 하는 제한은 부정형을 사용할 수 있습니다.

```
명확성 > 긍정 표현
```

# 14. 선택을 강요하지 않습니다

사용자가 스스로 다음 행동을 선택할 수 있도록 안내합니다.

### 지양

```
반드시 지금 상담하세요.
지금 바로 문의해야 합니다.
```

### 권장

```
의료진의 확인이 필요해요.

[의료진에게 문의하기]
```

단, 검수된 Recovery Protocol에서 즉시 의료진 확인이 필요한 상황으로 정의한 경우에는 안전성을 위해 필요한 행동을 명확하게 안내합니다.

---

# 15. 의료적 판단처럼 보이는 표현을 사용하지 않습니다

MALLO는 사용자의 피부 상태를 진단하거나 의료적 정상/이상 여부를 판단하는 서비스가 아닙니다.

### 사용하지 않기

```
정상이에요
문제없어요
안전해요
부작용이 아니에요
회복이 정상적으로 진행되고 있어요
걱정하지 않아도 돼요
```

### 권장

```
현재 조건에서는
가볍게 진행할 수 있어요.
```

```
오늘은 강도를 낮추는 게 좋아요.
```

```
오늘은 미루는 게 좋아요.
```

```
의료진의 확인이 필요해요.
```

# 16. 결과는 `결론 → 이유 → 근거 → 다음 행동` 순서로 보여줍니다

S08 Action Result에서는 사용자가 결과를 빠르게 이해할 수 있도록 다음 정보 위계를 사용합니다.

```
현재 Action / 선택 조건

↓

사용자용 Decision 문구

↓

핵심 결과

↓

판단 이유

↓

Recovery Protocol 근거

↓

다음 Action CTA
```

예:

```
운동 · 높은 강도

오늘은 미루는 게 좋아요

강도 높은 운동은
오늘 미루는 편이 좋아요.

판단 이유
...

Recovery Protocol
...

[나중에 다시 확인하기]
```

# 24. 그래픽 사용 기준

그래픽은 장식이 아니라 **상황을 이해하도록 돕기 위해서만** 사용합니다.

- 한 화면에서 핵심 그래픽은 가능하면 하나만 사용합니다.
- 의미 없이 여러 아이콘을 반복하지 않습니다.
- 그래픽 때문에 핵심 정보나 CTA가 아래로 과하게 밀리지 않게 합니다.
- 의미 없는 Gradient / Particle / 장식적인 AI 그래픽은 사용하지 않습니다.
- 현재 상황과 맞지 않는 경고 아이콘을 사용하지 않습니다.
- 불필요한 Loading 표현을 사용하지 않습니다.
- 이미지가 필요하다면 MALLO의 Medical Wellness 분위기와 맞는 고화질 이미지를 사용합니다.
- 그래픽보다 핵심 정보와 CTA가 먼저 읽혀야 합니다.

```

9. 하나의 모바일 기준 너비를 중심으로 설계합니다.
```

# 26. Bottom Tab 기준

MALLO의 Bottom Tab은 4개를 유지합니다.

```
Journey
Check
Ask
My
```

공통 Bottom Tab은 좌우와 하단에 여백이 있는 Floating 형태로 변경합니다.

구체적인 크기·간격·Radius·Shadow는 기존 MALLO 디자인 토큰과 화면 구조를 우선하며,
새로운 임의 토큰을 추가하지 않습니다.

### 기본 방향

```
╭──────────────────────────╮
│ Journey  Check  Ask  My │
╰──────────────────────────╯
```

## 기준

- 현재 선택된 탭을 명확하게 표시합니다.
- MALLO Red는 활성 상태에 제한적으로 사용합니다.
- 비활성 탭은 Secondary Text 계열을 사용합니다.
- 플로팅 영역은 White / Warm White 계열을 사용합니다.
- 과도한 Shadow를 사용하지 않습니다.
- Safe Area를 고려합니다.
- 콘텐츠와 Floating Tab이 겹치지 않도록 하단 여백을 확보합니다.
- Web에서도 기존 모바일 Viewport 안에 표시합니다.
- App / Web에서 Navigation 구조를 동일하게 유지합니다.

Floating Tab의 목적은 장식이 아니라 **현재 위치와 Navigation 영역을 명확하게 구분하는 것**입니다.

# 최종 기준

> **MALLO의 문구는 정보를 많이 설명하는 것보다, 사용자가 지금 무엇을 하면 되는지 이해하도록 돕는 것을 우선합니다.**

```
짧게
+
쉽게
+
한 번에 하나만
+
다음 행동이 보이게
+
사용자의 선택을 존중하게
+
의료적 경계는 명확하게
```

### 개발 시 가장 중요한 구분

```
개발자가 이해하기 좋은 이름
≠
사용자가 이해하기 좋은 이름
```

따라서 `TodayActionPlan`, `RecoveryRecord`, `POSTPONE` 같은 기존 코드/API 명칭을 무리하게 변경하지 않습니다.

**사용자에게 노출되는 문구만 MALLO의 UX Writing 기준에 맞게 변환합니다.**

# 텍스트 줄바꿈 기준

## 1. Headline / 핵심 결과 문구

- 의미 단위 줄바꿈이 UX상 필요한 경우에만 명시적 `\n`을 사용합니다.
- 특정 화면 크기에 맞추기 위한 임의 줄바꿈은 금지합니다.

## 2. Body / 설명 / 이유 / 안내 문구

- 명시적인 `\n`을 넣지 않습니다.
- 컨테이너 너비에 따라 자동으로 줄바꿈합니다.
- Web에서는 한글 단어가 글자 중간에서 분리되지 않도록 처리합니다.
- 예: `가\n볍게`처럼 한 단어가 중간에서 끊어지면 안 됩니다.

## 3. Button / Badge / Label

- 원칙적으로 한 줄로 표시합니다.
- 문구가 길다면 줄바꿈보다 문구를 간결하게 수정합니다.

## 4. 반응형

- 특정 Web viewport 또는 특정 모바일 기기에 맞추기 위해 문장마다 수동으로 `\n`을 추가하지 않습니다.
- Web / iOS / Android에서 공통으로 사용할 수 있는 구조를 우선합니다.
